# 0001. 시급을 근무 기록에 스냅샷으로 저장한다

- 상태: 채택
- 관련: `002_create_hourly_rates.sql`, `src/lib/services/hourly-rate.ts`

## 맥락

같은 근무자라도 조교와 코칭의 시급이 다르고, 시급 인상은 특정 날짜부터
적용된다. 그 이전 근무는 옛 시급으로 남아야 한다.

스프레드시트로 운영할 때 이 지점에서 사고가 났다. 시급 셀 하나를 고치면
지난달 확정된 급여까지 조용히 바뀐다. 정산이 끝난 뒤에 숫자가 달라지는데
아무도 모른다.

## 선택지

**(a) 조회 시 join해서 계산.** `hourly_rates`에서 `work_date`에 유효한 시급을
찾아 매번 곱한다. 정규화 관점에서 깔끔하고 중복이 없다.

**(b) 제출 시점의 시급을 근무 기록에 복사해 저장.** `work_logs`에
`applied_hourly_rate`와 `calculated_pay`를 둔다. 같은 값이 두 테이블에
존재하게 된다.

## 결정

(b)를 택한다.

(a)는 시급 행이 하나라도 잘못 들어가는 순간 과거 급여가 전부 다시 계산된다.
`effective_from`을 잘못 입력한 행 하나가 몇 달치 정산을 바꿀 수 있고, 이미
지급이 끝난 금액이라 되돌릴 방법도 없다.

급여는 "그때 얼마였는지"가 사실이어야 하는 데이터다. 계산으로 유도할 값이
아니라 기록해야 할 값이다. 중복 저장은 그 사실을 고정하기 위해 치르는 비용으로
본다.

## 함께 정한 것

`hourly_rates`는 수정하지 않고 계속 쌓는다(append-only). 시급을 바꾸면 기존
행을 UPDATE 하는 게 아니라 `effective_from`이 다른 행을 추가한다. 과거 시점의
시급을 나중에도 재현할 수 있어야 하기 때문이다.

유효 시급 조회는 이렇게 한다.

```
effective_from <= work_date
ORDER BY effective_from DESC, created_at DESC
LIMIT 1
```

`created_at` 2차 정렬이 있는 이유는 같은 `effective_from`으로 시급을 두 번
등록하는 실수가 실제로 가능하기 때문이다. 이 경우 나중에 등록한 값을 적용한다.

조회 성능을 위해 `(worker_id, role_type, effective_from DESC)` 복합 인덱스를
걸었다.

## 결과

시급을 바꿔도 이미 제출된 근무 기록의 금액은 변하지 않는다. 대신 시급을 잘못
입력해서 이미 제출된 기록을 고쳐야 할 때는 근무 기록 자체를 다시 제출해야
한다. 이 비용은 감수한다.
