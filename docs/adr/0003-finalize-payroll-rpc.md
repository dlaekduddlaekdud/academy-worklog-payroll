# 0003. 정산 확정을 Postgres 함수로 원자화한다

- 상태: 채택
- 관련: `009_finalize_payroll_fn.sql`, `src/app/(admin)/admin/payroll/actions.ts`

## 맥락

기존 `finalizePayroll`은 세 개의 독립 쿼리였다.

1. 해당 월에 대기 중인 근무 기록이 있는지 검사
2. 승인된 기록을 집계해 요약 행에 upsert
3. 요약 행의 상태를 `finalized`로 변경

①과 ③ 사이에 근무자가 기록을 제출하거나 다른 관리자가 승인하면, 확정된 금액과
실제 근무 기록이 어긋난 채로 확정된다. 일괄 확정은 근무자별 루프라 창이 더
넓었다.

금액을 바꾸는 연산에 트랜잭션 경계가 없는 상태였다.

## 문제

supabase-js는 여러 문장을 하나의 트랜잭션으로 묶을 수 없다. 클라이언트가
HTTP로 PostgREST를 호출하는 구조라 요청 하나가 트랜잭션 하나다. 앱 레이어에서
`BEGIN`/`COMMIT`을 흉내 낼 방법이 없다.

## 결정

연산 전체를 Postgres 함수로 내리고, 앱에서는 `supabase.rpc()` 한 번만
호출한다.

```
finalize_payroll(p_worker_id UUID, p_year INT, p_month INT) RETURNS void
```

함수 본문은 단일 트랜잭션에서 실행된다. 도중에 실패하면 요약 행도 남지 않는다.

**동시 확정 직렬화.** 요약 행을 `FOR UPDATE`로 잠근다. 같은 근무자·월에 대해
두 관리자가 동시에 확정을 눌러도 한쪽이 끝날 때까지 다른 쪽이 대기한다.

**권한 검사를 함수 안에서 한다.** `SECURITY DEFINER`는 RLS를 우회하므로
`is_admin()`을 직접 확인한다. 확정자(`finalized_by`)도 인자로 받지 않고
`auth.uid()`에서 가져온다. 호출자가 보낸 값을 신뢰하면 가입 트리거가
`raw_user_meta_data`의 role을 믿었던 것과 같은 종류의 취약점이 된다.

**일괄 확정은 함수를 반복 호출한다.** 전체를 한 트랜잭션으로 묶지 않는다.
한 명의 실패가 나머지를 막으면 안 된다는 것이 요구사항이라, 개별 실패를
허용하고 건너뛴 인원수를 함께 반환한다.

## 부수 효과

기간 계산이 SQL로 넘어가면서 버그 하나가 사라졌다. 일괄 확정이
`new Date(year, month, 0).toISOString()`으로 말일을 구하고 있었는데, KST에서
UTC로 변환되며 하루가 밀려 말일의 대기 기록이 검사 범위에서 빠지고 있었다.
같은 파일의 단건 확정은 `getDate()` 방식으로 올바르게 계산하고 있어서, 한
파일 안에 서로 다른 두 구현이 있고 하나만 버그인 상태였다.

이 경험 때문에 월 경계 계산을 `lib/utils/date-range.ts` 하나로 모으고, 그
함수들은 전부 로컬 시각 기준으로만 동작하게 했다.

## 결과

확정 도중 다른 변경이 끼어들 수 없다. 통합 테스트로 확인한다.

- 대기 기록이 있으면 예외가 나고 요약 행도 남지 않는다(롤백)
- 승인된 기록만 집계하고 반려된 기록은 빠진다
- 재확정해도 금액이 어긋나지 않는다
- 비로그인 호출은 거부된다

비용은 로직이 SQL로 옮겨가 앱 코드에서 읽기 어려워졌다는 점이다. 함수에 주석을
길게 달아 완화했다.
