# 0002-a. 승인된 기록도 수정할 수 있게 트리거를 제거한다

- 상태: **폐기.** [0002](0002-finalized-month-protection.md)로 대체
- 관련: `007_allow_approved_edit.sql`

이 문서는 이미 되돌린 결정을 남겨두기 위한 것이다. 당시에 무엇을 근거로
그렇게 판단했고 무엇을 놓쳤는지가 기록으로서 의미가 있다고 봤다.

## 당시 맥락

"승인된 기록도 수정할 수 있게 해달라"는 요구가 있었다. 근무자가 시간을 잘못
적어 제출했는데 관리자가 이미 승인해버린 경우, 고칠 방법이 없었다.

`work_logs`에는 확정된 월의 변경을 막는 트리거가 걸려 있었고, RLS 정책은
근무자가 `pending` 상태의 자기 기록만 수정·삭제할 수 있게 제한하고 있었다.

## 당시 결정

`007`에서 확정 월 보호 트리거를 제거했다. 마이그레이션에는 이런 주석을
달았다.

```sql
-- finalized 월 보호 트리거 제거 (앱 레이어에서 처리)
DROP TRIGGER IF EXISTS trg_work_logs_prevent_finalized ON public.work_logs;
```

## 무엇이 잘못됐나

세 가지가 겹쳤다.

**첫째, "앱 레이어에서 처리한다"가 사실이 아니었다.** 확정 월 검사를 하는
`assertNotFinalized` 호출은 `createWorkLog`에만 있었고 `updateWorkLog`와
`deleteWorkLog`에는 없었다. 트리거를 지우면서 앱 레이어를 확인하지 않았다.
결과적으로 두 레이어 모두 비어 있는 상태로 배포됐다.

**둘째, 요구를 잘못 해석했다.** 필요한 것은 "잘못 승인된 기록을 고칠 방법"
이었지 "승인된 기록을 제출자가 직접 고칠 권한"이 아니었다. 관리자가 승인을
취소해 `pending`으로 되돌리는 경로가 이미 있었는데 그걸 쓰지 않았다.

승인된 기록을 제출자가 고칠 수 있으면 승인 절차가 아무것도 보증하지 못한다.
관리자가 2시간을 승인했는데 근무자가 8시간으로 고쳐도 승인 도장이 유지된다면,
급여 도메인에서 이건 기능이 아니라 부정 경로다.

**셋째, 트리거만 지우고 RLS는 그대로 뒀다.** RLS는 여전히 `pending`만
UPDATE/DELETE를 허용하고 있었다. 그래서 실제로는 부정 경로가 막혀 있었지만,
대신 다른 버그가 생겼다. 근무자가 반려된 기록을 삭제하면 RLS가 0행을 매칭하고
supabase는 이 경우 에러를 주지 않는다. `if (error)` 검사를 통과해 성공으로
처리되고, 화면에는 삭제됐다고 뜨는데 DB에는 그대로 남았다.

## 교훈

방어를 제거할 때는 대체 방어가 실제로 존재하는지 확인해야 한다. 주석에
"앱 레이어에서 처리"라고 쓰는 것과 앱 레이어가 실제로 처리하는 것은 다르다.

그리고 supabase의 update/delete는 조건에 맞는 행이 없어도 에러를 내지 않는다.
`error`만 보면 실패를 놓친다. `.select()`로 영향 행 수를 확인해야 한다.
